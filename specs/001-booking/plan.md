# แผนทางเทคนิค: จองคิวตรวจสุขภาพ (Booking)

อ้างอิง: [spec.md](./spec.md) (`SPEC-BKG-001`)  
สถานะของแผน: ร่างจาก `Draft v1` โดยยังคง Open Questions ตาม spec

## 1. สรุปแนวทาง

1. ให้ผู้รับบริการที่ผ่านการยืนยันตัวตนแล้วเลือกแพ็กเกจ วัน และช่วงเวลาที่ว่างภายใน 30 วัน (`IF-IDP-01`, `FR-BKG-01`)
2. แยกการอ่านข้อมูลผู้รับบริการจาก HIS โดยใช้ HN ภายในระบบ และไม่เก็บเลขบัตรประชาชนในการจอง (`IF-HIS-01`)
3. ใช้การตรวจสิทธิ์การจองซ้ำและการตัดที่นั่งในธุรกรรมเดียว เพื่อรองรับการยืนยันพร้อมกัน (`FR-BKG-02`, `FR-BKG-03`, `FR-BKG-04`)
4. บันทึกการจองและสร้างงานแจ้งเตือนแบบ asynchronous เพื่อไม่ให้การจองรอ SMS/LINE (`FR-BKG-04`, `FR-BKG-05`, `IF-NOT-01`)
5. บันทึก audit log สำหรับการเข้าถึงข้อมูลสุขภาพและทดสอบตาม Acceptance Criteria ทั้ง 6 ข้อ (`DOM-PDPA-01`, `AC-BKG-01` ถึง `AC-BKG-06`)

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| MySQL | `CON-TECH-01` | ฐานข้อมูลหลักของการจอง โควตา งานแจ้งเตือน และ audit log |
| React (Vite) | ทีมเลือกเอง ไม่ได้มาจาก spec | หน้าจอเลือกแพ็กเกจ/วัน/ช่วงเวลาและแสดงผลการจอง |
| Python FastAPI | ทีมเลือกเอง ไม่ได้มาจาก spec | API สำหรับการค้นหาและยืนยันการจอง |
| TLS 1.2 ขึ้นไป | `NFR-SEC-01` | ใช้กับการรับส่งข้อมูลของระบบ |
| ตัวประมวลผลคิวงานแบบ asynchronous | `IF-NOT-01`, `NFR-REL-02` | กลไกที่ทีมเลือกเองเพื่อส่งคำขอ SMS/LINE และ retry ภายใน 5 นาที |

## 3. โมเดลข้อมูล

| Entity / ตาราง | ฟิลด์หลักที่จำเป็น | รองรับ |
|---|---|---|
| `patient_reference` | `hn` (อ้างอิงจาก HIS), ข้อมูลแสดงผลที่จำเป็นจาก HIS | `IF-HIS-01` |
| `package` | รหัสแพ็กเกจ, ชื่อแพ็กเกจ, สถานะ | `FR-BKG-01`, `FR-BKG-06` |
| `schedule_slot` | รหัสช่วงเวลา, วัน, เวลาเริ่ม/สิ้นสุด, รหัสแพ็กเกจ, โควตา, จำนวนที่นั่งคงเหลือ | `ASM-01`, `FR-BKG-01`, `FR-BKG-03`, `FR-BKG-04`, `FR-BKG-06` |
| `booking` | รหัสการจอง, `hn`, รหัสแพ็กเกจ, รหัสช่วงเวลา, วันตรวจ, หมายเลขคิว, สถานะ, เวลาสร้าง | `FR-BKG-02`, `FR-BKG-04`, `FR-BKG-05` |
| `notification_job` | รหัสงาน, รหัสการจอง, ช่องทาง SMS/LINE, สถานะ, จำนวนครั้ง retry, เวลาส่งครั้งถัดไป | `IF-NOT-01`, `FR-BKG-05`, `NFR-REL-02` |
| `audit_log` | ผู้เข้าถึง, เวลา, รหัสผู้รับบริการ, ประเภทการเข้าถึง | `DOM-PDPA-01` |

ไม่มีฟิลด์เลขบัตรประชาชนใน `booking` หรือ entity การจองใด ๆ; เลขบัตรประชาชนใช้เฉพาะตอนค้นผ่าน HIS ตาม `IF-HIS-01`

## 4. API / หน้าจอ

| รายการ | Input / Output หลัก | รองรับ |
|---|---|---|
| `GET /booking/packages` | Input: context การยืนยันตัวตน; Output: รายการแพ็กเกจ | `IF-IDP-01`, `FR-BKG-06` |
| `GET /booking/slots?package_id=&from=&to=` | Input: แพ็กเกจและช่วงวันที่ไม่เกิน 30 วัน; Output: วัน ช่วงเวลา และจำนวนที่นั่งคงเหลือ | `FR-BKG-01`, `NFR-PERF-01` |
| `POST /booking/confirm` | Input: แพ็กเกจ วัน และช่วงเวลา; Output: ผลสำเร็จพร้อมหมายเลขคิว หรือเหตุผลปฏิเสธ/ตัวเลือกใกล้เคียง 3 รายการ | `FR-BKG-02`, `FR-BKG-03`, `FR-BKG-04`, `FR-BKG-05` |
| `GET /booking/{booking_id}` | Input: รหัสการจอง; Output: รายละเอียดการจองและหมายเลขคิว | `FR-BKG-04`, `DOM-PDPA-01` |
| หน้าจอเลือกแพ็กเกจและช่วงเวลา | ผู้ใช้เลือกแพ็กเกจ/วัน/ช่วงเวลา เห็นจำนวนที่นั่งและผลคำนวณใหม่เมื่อเปลี่ยนแพ็กเกจ | `FR-BKG-01`, `FR-BKG-06`, `NFR-USE-01` |
| หน้าจอยืนยันผลการจอง | แสดงหมายเลขคิวเมื่อสำเร็จ หรือข้อความช่วงเวลาเต็ม/คิวเดิมเมื่อปฏิเสธ | `FR-BKG-02`, `FR-BKG-03`, `FR-BKG-04`, `FR-BKG-05` |

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| `CON-TECH-01` | ใช้ MySQL ในหัวข้อเทคโนโลยีและโมเดลข้อมูล | ใช้แล้ว |
| `DOM-PDPA-01` | ตาราง `audit_log`, การบันทึกผู้เข้าถึง/เวลา/รหัสผู้รับบริการ และ `GET /booking/{booking_id}` | ใช้แล้ว |
| `IF-IDP-01` | ตรวจ context การยืนยันตัวตนก่อน endpoint และหน้าจอที่เข้าถึงข้อมูลผู้รับบริการ | ใช้แล้ว |
| `IF-HIS-01` | `patient_reference` ใช้ HN และไม่มีเลขบัตรประชาชนใน `booking` | ใช้แล้ว |
| `IF-NOT-01` | `notification_job` และการเรียกตัวประมวลผล asynchronous หลังบันทึกการจอง | ใช้แล้ว |

| `AC-BKG-03` | `test_AC_BKG_03_offer_alternatives_when_slot_is_full` | ให้ผู้ใช้คนอื่นจองที่นั่งสุดท้ายก่อน แล้วพยายามยืนยัน ตรวจข้อความช่วงเวลาเต็ม ตัวเลือก 3 รายการ และไม่มี booking ซ้อน (`FR-BKG-03`) |

## 7. ลำดับงาน

1. กำหนดสัญญา input/output ของ IDP และ HIS และตรวจสิทธิ์ก่อนเข้าถึงข้อมูล (`IF-IDP-01`, `IF-HIS-01`)
2. สร้าง schema MySQL สำหรับ `patient_reference`, `package`, `schedule_slot`, `booking`, `notification_job`, `audit_log` โดยไม่เก็บเลขบัตรประชาชน (`CON-TECH-01`, `IF-HIS-01`, `DOM-PDPA-01`)
3. สร้าง API ค้นหาแพ็กเกจและช่วงเวลาภายใน 30 วัน พร้อมจำนวนที่นั่งคงเหลือ (`FR-BKG-01`, `FR-BKG-06`)
4. สร้างกติกาตรวจคิวเดิมและธุรกรรมยืนยันที่ตัดที่นั่ง/ออกหมายเลขคิว (`FR-BKG-02`, `FR-BKG-04`, `AC-BKG-01`, `AC-BKG-02`)
5. เพิ่มการตรวจการแข่งขันเมื่อช่วงเวลาเต็มและคืนตัวเลือกใกล้เคียง 3 รายการ (`FR-BKG-03`, `AC-BKG-03`, `Q-01`)
6. เพิ่มการสร้างงานแจ้งเตือนแบบ asynchronous และ retry (`IF-NOT-01`, `FR-BKG-05`, `NFR-REL-02`, `AC-BKG-04`)
7. เพิ่ม audit log และการป้องกันการรับส่งข้อมูลด้วย TLS 1.2 ขึ้นไป (`DOM-PDPA-01`, `NFR-SEC-01`, `AC-BKG-06`)
8. สร้างหน้าจอเลือกและยืนยันการจอง พร้อมวัด usability ตามเกณฑ์ 3 นาที (`NFR-USE-01`)
9. รัน test ตาม `AC-BKG-01` ถึง `AC-BKG-06` และทดสอบประสิทธิภาพตาม `NFR-PERF-01`

## 8. สิ่งที่ยังไม่ทำ

- `Q-01` “ช่วงเวลาใกล้เคียง” นับเฉพาะวันเดียวกัน หรือรวมวันถัดไปด้วย? -> ถามพยาบาลคัดกรอง  
  ส่วนการจัดอันดับและการเลือกตัวเลือกใกล้เคียงจะยังไม่สร้างจนกว่าจะได้คำตอบ
- `Q-02` หมายเลขคิวรีเซ็ตรายวัน หรือนับต่อเนื่อง? -> ถามเจ้าหน้าที่เวชระเบียน  
  ส่วนกติกาการสร้างหมายเลขคิวจะยังไม่สร้างจนกว่าจะได้คำตอบ
